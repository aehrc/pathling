# 14 — Date range annotation

**Spec:** `specs/001-parquet-on-fhir/spec.md` — FR-004, FR-021, FR-022, FR-023. Old tasks: T053, T065.

**What to build:** Dates carry the specification's range annotations, reflecting the stated precision, and the engine uses them as a fast path for date comparison where the schema carries them.

**A time without a timezone (owner, 2026-10-21).** A `dateTime` or `instant` with a time but no timezone is valid (decision 133's addendum). Its range annotation is the range the engine computes for it today, through `FhirPathDateTime`'s boundaries, so the annotation and the computed path agree. Whether that range should widen by ±14 hours is a follow-up in ticket 26.

**Where the kind lives (decision 135).** The range kind is defined once, in the kinds package beside `fhir-schema`'s annotation API. The engine's boundary UDFs (`LowBoundaryForDateTime` and its siblings, registered by `PathlingUdfRegistrar`) move onto it, so `FhirPathDateTime`'s boundaries, or a counterpart `fhir-schema` can reach, are the single computation. It is stored by the annotation step of ticket 11, not by the reader.

**The date grammar (decision 135, ticket 31).** Ticket 31 puts FHIR's date grammar in `fhir-schema` for `toDate()` and `toDateTime()`. The range kind, also in `fhir-schema`, parses dates with that grammar rather than a second one. Whichever ticket lands first puts it in place, and the other uses it.

**Placement (decision 135, part 4).** The range annotations are `_<element>.__start` and `__end`, fields of the date's metadata group, so a repeating date's bounds share the group's alignment with it. The group is stored for them before ticket 17 stores ids and extensions. The engine reads it by pairing the element with `_x`, naming only the annotation fields it needs, so that the read prunes (`evidence/annotation-pruning.md`).

**One computation for both bounds (owner, 2026-10-26).** `__start` and `__end` come from one parse of the date. Ticket 11's annotation step fills each annotation field separately, so as built it would parse every date twice. Change the step so that a kind is computed once per container, and its fields are filled from that one result. Ticket 12 raised this, where its quantity kind had two fields until the owner dropped `__canonical` (decision 137). The engine's fallback, where the schema carries no range, computes both bounds from one parse too.

**The annotations' type against the specification (owner, 2026-10-26).** The Parquet on FHIR specification gives `start` and `end` the physical type `int96` with the logical type `TIMESTAMP(isAdjustedToUTC=true, unit=MILLIS)`, and names `date` and `dateTime` as the types that carry them. Check what Pathling stores against that: Spark's `TimestampType` is adjusted to UTC at microseconds, and whether it is written as `int96` depends on `spark.sql.parquet.outputTimestampType`. Check also whether `instant` carries them, which the specification does not name. Match the specification where Spark can, and report each difference to the owner, to be recorded as a deviation as decision 137 records the quantity's, rather than settling it here. Ticket 30's layout column claims conformance, so a difference matters.

### Implementation (branch issue/2832_14_date-range-annotation)

**What was built, and where.**

- **The date grammar, in `fhir-schema` (decision 135, ticket 31).** `au.csiro.pathling.schema.date.FhirDateTime` holds FHIR's date grammar (moved from `FhirPathDateTime`, with `FhirPathTime`'s time grammar), the precision a value states, and its lower and upper boundaries. `FhirPathDateTime` delegates to it, so `FhirPathDateTimeTest` pins the moved code unchanged. Today's behaviour is kept: a missing timezone is taken as UTC, an hour above 23 is refused, and the upper bound is to the nanosecond. Ticket 31 can call it from `toDate()` and `toDateTime()`.
- **The kind.** `kinds/DateRangeKind`, on the range switch, carried in `__start` and `__end`, registered in `AnnotationRegistry.builtIn()`. `compute` is one UDF, `date_range`, returning `struct<__start timestamp, __end timestamp>` from one parse. It returns `java.sql.Timestamp`, as the engine's boundaries and `DateMatcher`'s literals did, so that Spark converts the stored and the literal bounds alike before the Gregorian cutover. A text outside the grammar fails it with the message the engine's UDFs gave. `LayoutFields` already put the bounds on `date`, `dateTime` and `instant`.
- **The annotation step computes a kind once per container (owner, 2026-10-26).** `Annotator.computingOnce` groups the annotations a container derives by kind, computes each kind whose fields are computed (absent, or recomputed) once, binding it to a lambda's argument (`element_at(transform(array(compute(v)), c -> container), 1)`), and fills each field from it or from the stored field. A kind none of whose fields is computed is not computed. This applies to metadata groups and to complex elements alike. The step no longer goes through `AnnotationKind.apply`; it resolves stored or computed itself, as it always did, from the schema it rebuilds.
- **The engine's fallback, one parse.** `TemporalComparator` takes each operand to a range struct and binds it once (`SqlFunctions.bindOnce`), so `canCompare`'s several reads of the bounds parse once; for a dateTime the range is `DateRangeKind.compute`, for a time the existing time UDFs. `DateMatcher` (search) computes a scalar date's two bounds from one `compute`, and a Period's lower bound of `start` and upper bound of `end` from one each. `LowBoundaryForDateTime` and `HighBoundaryForDateTime` and their registrations are removed; nothing in `server/`, `lib/` or elsewhere named them.
- **The engine's fast path.** A traversal to a singular `date`, `dateTime` or `instant` (`DefaultRepresentation.traverseDate`, and `ResourceRepresentation.traverse` at the root) returns a `DateRangeRepresentation`: the value is the stored text, unchanged, and beside it a range aligned with it, read per parent from `x` and `_x` with a new `ResolveFieldsOrElse` (in `encoders`, beside `ResolveOrElse`), which is `struct(_x.__start, _x.__end)` where the schema carries both and `compute(x)` otherwise, so the fallback parses once. Only `singular()` keeps the range; every other operation gives a plain `DefaultRepresentation`, so a range is never paired with a value it was not read with. (Superseded on 2026-10-27: see the owner's decisions and their implementation below, which keep it through more operations.) `Comparable` gains two hooks, `getComparisonOperand` and `getOperandComparator`, defaulting to today's behaviour; `DateTimeComparable` takes each operand's range (the one it was read with, or computed from the text) and compares ranges. The read prunes to `_birthDate:struct<__start:timestamp,__end:timestamp>`.
- **Docs.** `contracts/storage-layout.md` (a date range section and the type differences, left for the owner), `data-model.md`, and the annotation docs in `PathlingContext` (Java), `context.py` and `context.R`/`encoding.R`, which now say all three kinds are stored. **Left open.**

1. **Owner gate: an existing test's result changes for the same input.** `io/.../AnnotatorTest.leavesResourcesTheBuiltInKindsDoNotAnnotateAsTheyAre` feeds a Patient with `"birthDate":"1974-12-25"` and asserted that the step returns the same dataset (`assertSame`), because the built-in kinds then annotated only quantities. It is left unchanged and fails. A twin with a Patient carrying only `gender` is added; I recommend replacing the old test with it, as ticket 13's finding 7 was retargeted.
2. **The type against the specification (criterion 4), for the owner.** Probe: `evidence/scripts/ticket-14/RangeDeltaProbeTest.java`, output in `range-type-probe.txt` (Spark 4.0.2, Delta and plain Parquet behave the same):
    - **Physical and logical type.** The specification gives `int96` with `TIMESTAMP(isAdjustedToUTC=true, unit=MILLIS)`. Parquet cannot carry a logical type on `int96`, so the two cannot both be met. Spark's default `spark.sql.parquet.outputTimestampType` is `INT96`, and the footer is `optional int96 __start` with no logical type: the physical type matches, the logical type is absent. With `TIMESTAMP_MICROS` it is `int64 (TIMESTAMP(MICROS,true))`; with `TIMESTAMP_MILLIS`, `int64 (TIMESTAMP(MILLIS,true))`, the specification's logical type on another physical type. `isAdjustedToUTC=true` holds in every case Spark writes it.
    - **Unit.** The stored value is Spark's `TimestampType`, at microseconds; the upper bound of `1980` is `1980-12-31T23:59:59.999999Z`. Written as MILLIS it is truncated to `.999Z`, and the engine's results change, because the computed bound of a literal is at microseconds and the equal-ranges branch of the comparison no longer holds: `birthDate >= @1980` for a stored `1980` goes from `true` to empty, and `birthDate <= @1500-02-03` for a stored `1500-02-03` from `true` to empty. So matching the specification's unit would break criterion 3 unless the engine's computed bounds move to milliseconds too. I recommend recording a deviation: microseconds, written as Spark writes timestamps (int96 by default), with the reason above, as decision 137 records the quantity's.
    - **Types that carry them.** The specification names `date` and `dateTime`; Pathling also annotates `instant` (`LayoutFields`), so `meta._lastUpdated` is annotated in every resource that has it. I recommend keeping it and recording it, since an instant compares as a dateTime.
    - **Historic dates.** Spark 4's default rebase modes are `CORRECTED`, so 1850 and 1500 write and read back exactly; encoding and writing historic birth dates does not fail.
3. **What the fast path covers** (superseded on 2026-10-27: equality, repeating dates and date search now take the stored range). Comparison operators on a singular date read the stored range. Equality (`=`, `!=`, which `EqualityOperator` applies element-wise over collections), a repeating date (`Timing.event`), and date search (`DateMatcher`, applied per element inside `exists`) use the computed range, now from one parse. Each would need its range carried through further operations; candidates for ticket 26.
4. **The range is bound through a higher-order function** even where it is the stored struct, because which of the two it is is known only at analysis. This keeps the fallback to one parse but puts `transform` in the comparison, which falls out of whole-stage code generation and is not pushed down as a Parquet filter (nor was the UDF before). A candidate for ticket 26's performance follow-up; Spark's `With` expression could bind without it.
5. **A stored annotation is taken as given (`trust`).** Where the schema carries `__start` and `__end` but a row's are null, the comparison is empty rather than computed. An invalid date now also fails `encode`, as it fails a comparison in the engine; under `trust` both are undefined behaviour.
6. **Timestamp input.** The removed UDFs also accepted a `Timestamp` column. No date the engine builds is one, so the kind takes text only.

### Owner's decision on the representation (2026-10-27)

A difference in representation is not expressed as a subclass of `ColumnRepresentation`, because the subclass is not preserved by every operation, as `DecimalRepresentation` was not before it was removed (`8cf5363773`). The type-specific logic belongs in the collection classes. `DefaultRepresentation`'s purpose is to unify singular and plural columns, and it is not given a second one.

Until the engine reads a primitive's metadata (ticket 17), a FHIR `date`, `dateTime` or `instant` carries nothing beyond its value and its range, so there is no difference between it and a System date. A traversal to one converts it to a System date, as a FHIR `decimal` is converted to a System decimal: a structure of its text and its range, whose range is the stored annotations where the schema carries them and is computed from the text otherwise. The range is computed as the date is traversed, whether it is compared or not. A text outside FHIR's date grammar is not conformant, so under `trust` it is undefined behaviour (ticket 31): it fails `date_range`, which is left as it is.

### Implementation of the owner's decision on the representation (2026-10-27)

- **The System date.** `fhirpath`'s `column.SystemDateTime` builds and reads it: `struct(value: string, range: struct<__start, __end>)`. The range is nested rather than flattened beside the value, so that a range computed from the text is one call of `date_range` for both bounds. `fromStored` and `fromStoredArray` take a date and its metadata group, the second pairing a repeating date's texts and groups by position, as `DateRangeRepresentation.rangeOf` did; `fromText` computes the range; `fromLiteral` computes it as the query is built, from `FhirDateTime`, so a literal is never parsed per row; `empty` is a typed null.
- **Traversal converts.** `DefaultRepresentation.traverseDate` and `ResourceRepresentation.traverse` build System dates. Each parent is bound with `let`, so a parent that is not deterministic, such as a `trace()`, is evaluated once for both the date and its group.
- **The collections.** `DateCollection` and `DateTimeCollection` hold System dates, from literals and `fromValue` as well. `Collection` gains `getOutputColumn()`, the values as a caller of the engine is given them, by default the column as it is held; the two date collections give the text, and their `toExternalValue()` and `asStringPath()` are built on it. `TemporalComparator.forDateTime()` reads the range each operand carries, still bound once (owner's decision 5). Because the range is inside the item, `where`, `select`, `first`, unions and every other operation keep it, and nothing special is needed for them.
- **Conversions and other builders.** `toString()` of a date gives its text; `toDate()` and `toDateTime()` from a string give a System date, and from anything else a typed empty one. `property(..., 'dateTime')` converts the looked-up text. A date search reads the range of the System date it is given; a Period's dates are read as before.
- **Readers of results.** `SearchColumnBuilder.fromExpression`, and with it `PathlingContext`'s expression-to-column API, `SingleInstanceEvaluator`, and the YAML and DSL test executor read `getOutputColumn()`, so a date reaches a caller as its text, as it did before.
- **Removed.** `DateRangeRepresentation`; the operand hooks `getOperands` and `getOperandComparator` on `Equatable` and `Comparable`; `ColumnRepresentation.bound`, `filterItems` and `transformItems`, with `Collection.filter` and `project` back as they were; `ElementMatcher.matchAny`, with `SearchFilter` back as it was; `TemporalComparator.forDateRanges`; and `SqlFunctions.isDeterministic`, back inside `let`. `bindOnce` stays.
- **Review findings.** This settles the trace firing more than once per row in a date traversal, the `where` condition evaluated twice per item, and `bound`'s reliance on the identity of a column. The two comments in `DateMatcher` now end with full stops, which the review fixes above said they did but they did not.
- **What an output date costs.** A root date that is only output, not compared, neither parses its text nor reads its annotations, because the optimiser drops the unused range (`anOutputRootDateNeitherParsesNorReadsItsRange`). A date under a repeating parent (`name.period.start`) or a repeating date (`timing.event`) is converted inside a lambda, where the range is not dropped: output alone parses each date once where the schema carries no annotations, and reads the annotations, parsing nothing, where it does.
- **Tests.** `DateRangeComparisonTest.theComputedRangeTakesOneParse` expects the stored date to be parsed once and the literal not at all. `ElementMatcherTest`'s date cases and `ComparisonTraceTest`'s temporal cases give the matcher and the comparator System dates, which is what the engine gives them.
- **Not changed.** `trace()` on a date logs the System date, not its text, because the trace logs the value it passes on.

### Owner's decisions on the third review (2026-10-28)

A medium-effort code review of the branch against `issue/2832` reported ten findings.

1. **A text that is not a date converts to empty.** `toDate()` and `toDateTime()` of a text that follows the grammar but names a date or time that does not exist, such as `'2023-02-30'`, `'2023-13'` or `'2023-06-15T25'`, give empty, and `convertsToDate()` and `convertsToDateTime()` give false, as the FHIRPath specification's "not convertible" and fhirpath.js 5.1.0 (`hasValidDateComponents`) do. The range of a stored text, at ingest and in traversal, still fails on such a text, which is ticket 26's follow-up on non-conformant data.
2. **A leap second and a long fraction are dates.** FHIR allows `:60` and a fraction of any length. `FhirDateTime` takes a leap second as the second before it, as fhirpath.js does, and a fraction to the nanosecond.
3. **The bounds are the true instants.** The range annotation, a literal's range and a search value's bounds are given to Spark as `Instant`s, not `Timestamp`s, which Spark rebased from the Julian calendar in the JVM's time zone before the Gregorian cutover. 4. **The server.** Left to the server's migration, #2837, where the setting and the writes it covers are noted in a [comment](https://github.com/aehrc/pathling/issues/2837#issuecomment-6459415645). Decision 138 records it.
5. **The binding in a comparison and a date search.** Added to ticket 26's candidate on the binding of a date's range, with why removing it alone would not push the filter down.
6. **What an output date costs.** Already ticket 26's candidate (decision 4 above); no change.
7. **Java's `create()` takes an existing session as it is,** as Python's does. This changes decision 8 above, which kept decision 138 as it stood. Decision 138 is amended.
8. **Reading a stored range through `AnnotationKind.read`.** No change: the date range kind does not override it, and a range stored at another type is ticket 26's follow-up on non-conformant data.
9. **One `bindOnce`.** It moves to `fhir-schema`, which `io` and `fhirpath` both use, and the annotation step's copy is removed.
