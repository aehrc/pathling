# Annotations in the engine: decision structure

Draft for working through `specs/001-parquet-on-fhir/design/annotations-in-the-engine.md`.
Sources: the owner's statements in the design session, the design doc as it now stands
(uncommitted), and the five `evidence/annotations-design-*.md` write-ups. Nothing here is
a conclusion. Gaps are marked **GAP** and are the owner's to fill.

## 0. Framing (owner, 2026-11-03)

**Co-design.** The PoF spec's annotation layout and the Pathling engine are one design
problem. Engine performance is a legitimate driver for the spec.

Context from the owner:

- **Decision rights differ.** The PoF spec is owned and proposed by a colleague active
  in the FHIR standards space; the engine is the owner's. Spec decisions (D3c, D4, D5,
  D6) end with the colleague.
- **The spec's priority is interoperability:** various consumers can access and consume
  the data efficiently. The proof is adoption by a few implementations. Pathling is the
  first, and must be able to use it. Other consumers are uncertain (possibly FlatQuack).
- **Nothing is irreversible until the spec is officially released.** Designs that let the
  implementation progress, with a path to change parts later, are acceptable. Release is
  the one-way point, not any decision before it.
- **The engine should separate its internal FHIR/System representation from the PoF
  layout,** so either can be swapped. PoF need not be the engine's native schema; a
  different, less interoperable but easier one is allowed, **as long as it does not
  create a different binary format.**

Consequences for the process:

- Spec and engine decisions are scored in one structure, against both sets of criteria
  in §3, but recorded for different deciders.
- The door column below now means "one-way **at spec release**". Before release every
  decision is two-way; keeping a path to change becomes a criterion (K10).
- A spec choice driven by an engine measurement records that driver in the R-entry, so
  the colleague and other implementers can judge it.

## 6. Process observations

- **Scope.** D3b is an engine-wide change, not an annotations change. It may deserve
  its own decision, with the annotations design depending on it.
- **Ordering.** Spec decisions (D4, D5, D6) gate the spec release; engine decisions can
  be deferred.
- **Coupling at the crux.** The spec choice D4 depends on whether D3b is viable,
  which is the least-evidenced item (S9).
- **No stopping rule yet.** Nothing says what evidence would close D1 or D3.
- **K11 (formerly C8) changes the shape of the problem.** With a seam between the PoF layout and the
  engine's internal form, D2 (what the element carries) and D4 (where annotations are
  stored) may no longer be the same decision. Whether they decouple is open.
- **The evidence is all Spark.** K9 is the colleague's priority, and nothing on file
  measures a second consumer.

**Owner's correction (2026-11-03).** The complex-parent lambda limitation is old, but the PoF
layout makes it worse. Legacy keeps all extensions in one resource-level `_extension` map keyed by
`_fid` (encoders `ExtensionSupport`), so a complex element carries only an integer `_fid` and
reading it whole in a lambda is cheap. PoF stores extensions inside each element
(`period.extension`, `_start.extension`), so the whole read now carries their payload. This
applies to complex elements' own extensions too, not only to primitives, and `__x` does not
address it.

**Structural fact.** The options are not mutually exclusive. `__x` does not cover a lambda over
a complex parent (S4), which only D3a or D3b removes. C4's baseline is legacy, so S4 is in scope and D3a or D3b is required. The choice is between
combinations: D3a alone, D3b alone, D3a + `__x`, D3b + `__x`. `__x` is now an addition to an
engine fix, not an alternative to one.
