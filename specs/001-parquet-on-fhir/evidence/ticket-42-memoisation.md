# Ticket 42: memoised annotation computations, measured

The measurements ticket 42 asks for (`issues/42-shared-annotation-computation.md`, step 4), taken
after each annotation became its own scalar computation over a computation memoised per thread
(decision 145, design §4.6): the two bounds of a date, `date_start` and `date_end`, over one parse,
and the two canonical annotations of a quantity, `quantity_canonical_code` and
`quantity_canonical_value_exact`, over one canonicalisation.

**Results.**

- **Each value is computed once, in every context measured.** Over distinct values, so that no
  value is spared by one cached before, the parses of dates equal the dates, and the
  canonicalisations equal the quantities: as two projected columns, in a comparison that reads
  the lower bound three times and the upper bound twice, in a date search, inside a `transform`
  lambda, inside a `filter` lambda, with the bounds read in two separate passes over an array, and
  in the engine's own conversion of a repeating date, which reads them in two passes.
- **A traced input fires once.** A traced text converted to a date, a traced System date compared
  or searched, and a traced time compared, are each evaluated once per row, however many of the
  bounds are read.
- **Date comparisons and searches are faster; two contexts are slower (first measured at
  `7d22534b9f`).** Against the build before the change, on the engine's computed path, a comparison inside a lambda
  takes 28% to 36% less time and a date search 20% to 25% less, in each of three rounds. Two
  contexts are slower: annotating quantities, by 28%, 6% and 15% in the three rounds, and a date
  that is only output under a repeating parent, by −2%, +4% and +7%. A quantity comparison and the
  annotation of dates are unchanged within the spread between rounds. On the existing JMH
  benchmark, encoding, which annotates, is as fast or faster for every resource type in both orders
  of running the jars, and view execution over annotated data shows no slowdown beyond JMH's error.
  See [Throughput](#throughput).
- **The quantity slowdown, profiled, reduced and accepted (owner, 2026-11-10).** It is the second
  function call: a cache lookup and a second conversion of the quantity, while encoding the output is
  negligible. Comparing the last input first, and passing the three fields as columns of their own,
  brought the two annotations from 19–21% to 9–11% above one grouped function. The rest is accepted.
  The output-only date is 6% to 9% slower until ticket 43. See
  [Profiling the quantity slowdown](#profiling-the-quantity-slowdown-owner-2026-11-10).

## Conditions

- Spark 4.0.2, Java 21, `local[4]` on an Apple M3 Pro with 11 cores, macOS 27, session time zone
  UTC, adaptive execution off. Photon and Databricks are not measured (owner, 2026-11-10; #2889).
- Branch `issue/2832_42_memoise-annotations`. The build before the change is `3e5c4829a4`, the
  baseline plan tests on `issue/2832` at `d4ee59b73e`; the build after it is `7d22534b9f`. The
  parse counts were taken at `7d22534b9f`, with the test's rows read back from Parquet as
  committed after it.
- Each value is cached by its text (for a quantity, its value, system and code) in a
  least-recently-used cache of 64 entries per thread. A computation that fails is not cached.

## The parse runs once per value

`fhirpath/.../column/AnnotationMemoisationTest` counts the parses that `DateRangeKind` makes, and the
canonicalisations that `QuantityCanonicalKind` makes, while a query runs into the `noop` sink. The
counter counts misses of the cache, across all task threads. Each test reads 500 rows of values
that no other test uses, so the cache never holds a value beforehand, and the count is the number
of computations. The date tests, and the engine's conversion of a stored quantity, read their rows
from Parquet written in four files, so that the query runs in Spark's tasks rather than being
folded over local rows on the driver. The quantity computed as two columns is generated by
`spark.range` in four partitions, which also runs in tasks. The repeating quantity at ingest
(`io/.../QuantityCanonicalAnnotationTest.aRepeatingQuantityIsCanonicalisedOncePerQuantity`) reads
one local row, which Spark may evaluate on the driver; the count holds either way, because the
cache is per thread.

| Context | Values | Computations | Per value |
| --- | --- | --- | --- |
| Both bounds of a singular date as two columns | 500 | 500 | 1.000 |
| A singular date compared with a literal (`__start` read 3 times, `__end` twice) | 500 | 500 | 1.000 |
| A singular date searched (`eq`) | 500 | 500 | 1.000 |
| Both bounds inside a `transform` lambda, arrays of 3 | 1,500 | 1,500 | 1.000 |
| A comparison inside a `filter` lambda, arrays of 3 | 1,500 | 1,500 | 1.000 |
| The bounds in two separate passes, `transform(a, start)` and `transform(a, end)` | 1,500 | 1,500 | 1.000 |
| The engine's conversion of a repeating date, which reads the bounds in two passes | 1,500 | 1,500 | 1.000 |
| Both canonical annotations of a quantity as two columns | 500 | 500 | 1.000 |
| The engine's conversion of a stored quantity without annotations (`QuantityEncoding.fromStored`) | 500 | 500 | 1.000 |
| A repeating quantity at ingest, `component[].valueQuantity` through the annotation step | 50 | 50 | 1.000 |

The plan computes a bound wherever it reads one, so the plan text no longer counts parses: a
singular comparison holds five calls, three of `date_start` and two of `date_end`
(`DateRangeComparisonTest.theComputedRangeTakesOneParse`). At run time they are one parse.

Two more checks run in the ordinary suite. `io/.../DateRangeAnnotationTest.bothBoundsComeFromOneParse`
asserts that annotating a singular date, a date under a repeating parent and a repeating date
computes each bound once in the plan and parses no more dates than there are.
`fhir-schema/.../PerThreadLruCacheTest` asserts that two passes over 64 values compute each once,
that the least recently read value is evicted, that a failure and a null result are not cached,
and that each thread has its own cache.

Within a run, the five times were within 5% of the median except for two outliers (round 1, before:
the comparison in a lambda, 2961 against 2547, and the search, 674 against 468). Between rounds,
the same jar moved by up to 11% (before: `quantity-compare` 746, 826 and 838; the comparison in a
lambda 2547, 2326 and 2256). A change is read as real only where it exceeds that in every round.

- **Dates.** The comparison in a lambda and the search are faster in every round, beyond the
  spread. The singular comparison is faster in two rounds. The struct the range was built as is no
  longer built, nor bound with `bindOnce`.
- **A date only output under a repeating parent: slower in two of three rounds, for the owner.**
  Its range is still computed, now as two bounds rather than one structure, and nothing reads it.
  The time after the change is steady (1331, 1326, 1333) while the time before fell from round to
  round (1365, 1275, 1241), so the size of the change is uncertain; it is within the spread between
  rounds, but on the slower side in rounds 2 and 3. Making this date compute nothing is ticket 43's.
- **Annotating quantities: slower in every round, for the owner.** Where one function
  canonicalised a quantity and returned both fields, two are now called, and the second is a cache
  hit. The cause is not measured. A likely one is that each call converts the quantity structure to
  a row and builds a key for the cache; ticket 12's evidence found a cost of the same kind in two
  call sites for one comparison (`ticket-12-quantity-annotations.md`). The quantity comparison over
  unannotated data, which calls both functions too, is within the spread. Nothing has been done
  about it; the ticket brings any slowdown to the owner first.

### Profiling the quantity slowdown (owner, 2026-11-10)

The owner asked for the cause of the slower annotation of quantities, and a fix if one is cheap.

Every table below gives the build it was measured at. `scripts/ticket-42/run-cost.sh` runs any of
`QuantityCostProbe`'s variants against a shaded benchmark jar. The variants that call the kind
(`both`, `code-only`, `both-narrow`, `code+*`) measure the kind of the jar they run against: at
`5fec8fb57d` and later, the engine and the annotation step pass the kind its three fields as
columns, and the kind's structure form, which those variants call, reads the fields from the
structure again. Run at HEAD, they therefore do not reproduce the tables measured at `7d22534b9f`
and `2d9da8b3e0`, the "variant 2, whole structure" ones; the replica and constant variants do not
depend on the build.

**Cause, measured** (at `7d22534b9f`). `scripts/ticket-42/QuantityCostProbe.java` runs variants of the canonical
annotations over the probe's 1,000,000 Observations against the jar of `7d22534b9f`, each in its
own JVM, alternated, nine runs each, median milliseconds:

| Variant | Run 1 | Run 2 |
| --- | --- | --- |
| The old form: one function returning the code and the value as one structure, uncached | 329 | 334 |
| `__canonical_code` alone, a cache miss on every row | 333 | 341 |
| Both annotations, the second a cache hit | 423 | 406 |

The first function, with its cache, costs what the old single function did. The whole difference is
the second call, about 80 ns a quantity. JFR samples and further variants split it into: converting
the quantity structure to a row a second time, about 20 ns (its four strings are decoded again);
building the key, about 10 ns; and the cache lookup, the rest: hashing the three freshly decoded
strings, comparing them, and reordering the access-ordered map. Building `RowFields`' error message
eagerly costs nothing measurable, and passing only the three fields the kind reads saves about 3%.

**The cheap fix applied** (`2d9da8b3e0`): the cache compares the input with the one it read last
before hashing it, since the annotations of one value read it one after the other. In the same
probe, the cost of both annotations fell from about 410 to 365 ms against 313 for the old form:
the extra cost of the second call fell from about 85 to 55 ns. The rest, a second conversion of the
structure and a comparison of three strings, comes with calling a second function at all.

**Re-measured** (at `2d9da8b3e0`) with the engine probe, three rounds as before (before then after in rounds 1 and 2,
after then before in round 3), the build before ticket 42 against `2d9da8b3e0`:

| Context | Round 1 before / after | Round 2 before / after | Round 3 before / after | Change |
| --- | --- | --- | --- | --- |
| `birthDate > @1980` | 408 / 370 | 369 / 356 | 373 / 373 | −9%, −4%, 0% |
| `name.where(period.start > @2001-06).count()` | 2383 / 1613 | 2261 / 1575 | 2258 / 1664 | −32%, −30%, −26% |
| `name.period.start` (output only) | 1313 / 1365 | 1233 / 1339 | 1245 / 1345 | **+4%, +9%, +8%** |
| `birthdate=ge1980` (search) | 455 / 368 | 433 / 348 | 433 / 369 | −19%, −20%, −15% |
| Annotating the Patients | 1871 / 1835 | 1799 / 1808 | 1816 / 1920 | −2%, +1%, +6% |
| `value.ofType(Quantity) > 50 'mg'` | 828 / 810 | 840 / 797 | 855 / 894 | −2%, −5%, +5% |
| Annotating the Observations | 481 / 526 | 480 / 532 | 470 / 570 | **+9%, +11%, +21%** |

Round 3, which ran the build after the change first, is slower for it in every context, so it
carries an order effect. Against the first measurement (+28%, +6%, +15%), the annotation of
quantities is still slower by about 10% to 20%: the fix closes part of the gap, not all of it.

**No cheap fix closes the rest, so it goes back to the owner.** What remains is the cost of a
second function call over the same structure. The options:

1. Accept it. It falls on ingest only, about 50 ns a quantity, and `encode` of Observations is still
   faster overall (above).
2. Pass the kind only the fields it reads, from the schema the annotation step observes, for a
   change to the annotation step's interface: about 3% as a narrower structure, and about 6% as
   separate arguments (measured below).
3. Compute both canonical annotations at ingest from one call, as one structure whose two fields are
   stored flat, bound once per quantity. The stored layout stays flat, and the engine keeps its
   scalar functions, but ingest groups the computation again, which decision 145 set aside.

**The date only output under a repeating parent moved too.** It is slower in all three new rounds,
+4% to +9%, beyond the spread of the build after the change (1339 to 1365), where the first
measurement read −2%, +4% and +7%. Both bounds are computed for each date and nothing reads them;
the fast path makes the second bound a cheaper hit but does not remove the call. Ticket 43 makes
this date compute nothing, which removes the cost rather than reducing it.

#### Passing only the fields the kind reads, measured (owner, 2026-11-10)

The owner asked for the "about 3%" of option 2 to be measured. That figure came from passing a
narrower structure, `struct(value, system, code)`, which still converts a row. The variants below
pass the three fields as separate arguments instead. `QuantityCostProbe` again, against the jar of
`2d9da8b3e0`, the same 1,000,000 Observations, each variant in a JVM of its own, nine runs, two
alternated rounds. The replica variants run the kind's memoised canonicalisation, with the same
cache and last-input check, in the probe's own functions, so that only the form of the input
differs between them. Median milliseconds:

| Variant | Round 1 | Round 2 | Second call, ns a quantity |
| --- | --- | --- | --- |
| 1. The old form: one function returning code and value as one structure | 306 | 308 | none |
| 5. `__canonical_code` alone, today's code (lower bound for two calls) | 328 | 336 | none |
| 2. Today's code: two functions over the whole structure | 365 | 372 | 37, 36 |
| Replica of 2: two functions over the whole structure, read by name | 397 | 392 | 61, 65 (against its own code alone: 336, 327) |
| 3. Two functions taking `value`, `system` and `code` as separate arguments | 344 | 349 | 23, 49 (against its own code alone: 321, 300) |
| Bound, not a design: the second call keyed by `xxhash64` of the undecoded strings, taking no strings | 337 | 360 | 4, 24 |

- **Against today's code, variant 3 is 6% faster** (365 to 344, 372 to 349), and against the
  replica over the whole structure 12% faster. The gap to the old form falls from 19% to 21%
  (today) to 12% to 13% (variant 3). So "about 3%" understates passing separate arguments; it
  held for the narrower structure it was measured on, which still converts a row.
- **Where variant 3 saves.** It skips converting the quantity structure to a row, twice, and
  reading its fields by name; Spark passes the three strings directly. Decoding the strings is not
  the main remaining cost: the bound that decodes no strings for the second call is no faster than
  variant 3 (337 and 360 against 344 and 349). What remains is the cost of a second function call as
  such.
- **The replica of 2 is slower than today's code** by 20 to 30 ms, although it does the same work;
  the two rounds agree on it, and the cause was not looked into. The comparison of 3 with 2 is
  therefore given both against today's code and against the replica.
- **Variant 4 is not feasible in `fhir-schema`.** A Java or Scala function registered through the
  public API receives its string arguments as Java strings, decoded by Spark before the call, so a
  key that compares the stored bytes without decoding them needs a Catalyst expression over
  `UTF8String`. That is internal API, which `fhir-schema` may not use (CONTRIBUTING.md). It could
  live in `encoders`, beside `ResolveOrElse`; the bound above suggests it would gain little.
- In the engine probe's annotation of Observations, which also writes the numeric annotation and
  rebuilds the quantity, these savings are a smaller share of the whole.

#### Input or output: where the second call's cost goes (owner, 2026-11-10)

The owner suspected that the cost lies in encoding the functions' results, the structure
`{value DECIMAL(38,0), scale}` that `__canonical_value_exact` returns, rather than in decoding their
inputs. `QuantityCostProbe` again (`2d9da8b3e0`, the same data, a JVM per variant), fifteen runs,
three alternated rounds. Two kinds of variant split the cost:

- **Constant functions**, which convert the quantity structure and return a constant without any
  cache, so the canonicalisation's 250 ms does not drown the differences: one call returning the
  code (`const-code`), plus a second call returning null (input conversion only), a string, the
  unscaled `DECIMAL(38,0)` alone, or the value structure.
- **Replica functions**, with the kind's memoised canonicalisation: the code alone, plus a second
  call returning the code again from an equal structure (input, cache hit, string output), the value
  structure (as today), or the unscaled decimal alone (variant 6, not a valid layout).

Medians, milliseconds:

| Variant | Round 1 | Round 2 | Round 3 |
| --- | --- | --- | --- |
| `const-code` | 68 | 58 | 71 |
| + a second call returning null | 89 | 80 | 80 |
| + a second call returning a string | 78 | 72 | 82 |
| + a second call returning the unscaled decimal | 93 | 89 | 91 |
| + a second call returning the value structure (variant 7) | 87 | 85 | 100 |
| Replica, code alone | 315 | 319 | 378 |
| Replica, + the code again (cache hit, string output) | 382 | 379 | 390 |
| Replica, + the value structure (as today) | 375 | 394 | 385 |
| Replica, + the unscaled decimal (variant 6) | 368 | 370 | 380 |

Round 3's replica of the code alone is an outlier (378 against 315 and 319), so the replica's
differences are read from rounds 1 and 2.

The second call's cost, in nanoseconds a quantity:

| Part | Measured as | Round 1 | Round 2 | Round 3 |
| --- | --- | --- | --- | --- |
| Converting the input | constant, second call returning null, less `const-code` | 21 | 22 | 9 |

| The whole second call, unscaled decimal (variant 6) | replica | 53 | 51 | |

**The owner's hypothesis does not hold.** Encoding the structure costs between nothing and about
20 ns, at the level of the noise, and returning the unscaled decimal alone instead saves between 7
and 24 ns in the replica. Most of the second call is the cache work, about 50 ns: reading the three
fields by name, building the key, comparing it with the last input and, on that path, rebuilding
the exact value's row. Converting the input structure is the next part, about 20 ns. The replica's
second call is dearer than today's code's (37 ns in the measurement above), so these parts are
read as proportions rather than as today's exact costs.

## Behaviour changes that no probe measures

- **A quantity field that is not text is cast to text at ingest.** Since `5fec8fb57d` the annotation
  step reads a quantity's `value`, `system` and `code` as text columns, cast to a string, where
  before a field of another type failed the canonicalisation with an `IllegalArgumentException`.
  Conformant data always has text there, so only the way wrong input fails changes. The kind's
  structure form, which a caller without the schema uses, still fails on a field that is not text.
- **A time comparison computes its bounds where it reads them** (`7a7505702c`, owner,
  2026-11-10, decision (c) of the gates). `TemporalComparator.forTime()` binds the operand with
  `SqlFunctions.let` and no longer materialises the two bounds with `bindOnce`, so each comparison
  computes `LowBoundaryForTime` three times and `HighBoundaryForTime` twice per operand. They are not
  memoised. No probe measures it.

## Open points

- **A cheaper last-input check, candidate for #2889 (owner, 2026-11-10).** The check builds the key,
  a list of the three strings, before comparing it with the last input. Comparing the three inputs
  with the last ones first would build no key and allocate nothing on the path the second
  annotation of a value takes.
- **Keying on the stored bytes, candidate for #2889 (owner, 2026-11-10).** A function registered
  through the public API receives its strings decoded. A Catalyst expression in `encoders`, beside
  `ResolveOrElse`, could compare the stored `UTF8String` bytes with the last input's without decoding
  them. The bound measured above suggests the gain is small.
- **Grouped or flat annotations** (design §6, question 1): the ingest cost above is recorded there
